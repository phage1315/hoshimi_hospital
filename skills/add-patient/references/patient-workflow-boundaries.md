# Patient workflow boundaries and handoffs

Use the smallest workflow that covers the current request. Each row is an independent completion claim; completing one row does not imply the later rows are done.

| Workflow | Required input | Allowed changes | Deliverable | Completion gate / handoff | Pause and ask when |
|---|---|---|---|---|---|
| **Pure patient-data import** (`import-patient-data`) | Source bundle or confirmed patient identity, adult age, traits/personality proposal, and patient-authored text/data available for this phase | Only the target `data/patients/<id>/patient.json`, its one index entry when new, needed English localization entries, and a scoped import record. No image writes or CG pool integration. | Schema-valid patient bundle loaded through the shared loader, registered once, with required text localized/tested. | Claim only “patient data imported.” Handoff names missing portrait keys/assets and any later user-supplied asset/CG work. Does not mean game-ready. | Duplicate identity/ID; adult status or source meaning unclear; dialogue or medical source text conflicts with required schema; unsupported enum; unresolved required reference; user text would need invention or rewrite. |
| **Required SFW portrait generation** (`generate-patient-portraits`) | Existing indexed patient bundle, confirmed identity/seed/reference images, and explicit request to generate required SFW portraits | Only generated SFW portrait files, their runtime portrait mappings, generation/audit evidence, and related asset-source documentation. No patient identity/data rewrite, no user-supplied nude art, and no full-screen CG. | Each requested key either accepted and mapped, or explicitly blocked/missing with evidence; no unreviewed image is counted as complete. | Claim only the verified SFW portrait stage. User reviews the six base images before dependent variants; afterwards report any remaining portrait or runtime UI checks. | Identity/reference role unclear; required reference absent; ambiguity changes pose/coverage/class; a base fails review; tool blocks a requested image and a compliant, faithful path is unclear; user asks to stop. |
| **Supplied asset import for existing patient** (`import-patient-assets`) | Existing indexed patient bundle, user-provided files, and a user description of each file's intended use | Only listed asset files, target patient's portrait/pool references, asset provenance/import report, and asset-source documentation. No new patient creation, SFW ImageGen, or unrelated asset completion. Full-nudity illustrations and NSFW/full-screen CGs belong here. | Each supplied item marked integrated/blocked/not requested; accepted assets resolve from the intended runtime UI/action and do not leak to other patients. | Claim only the named assets are connected. Do not report whole-patient completion unless all separately required patient-data and SFW stages have passed. | Patient does not yet exist; image-to-description match is ambiguous; no unique runtime node mapping exists; candidate nodes have materially different branches; image semantics conflict with the selected node; source asset is missing/corrupt or an operation would alter it beyond authorization. |

## Scope rules

- “Add/import patient” does not automatically authorize all three workflows. If the user requests several stages, execute only those stages and preserve the handoff order: patient data first, then required SFW generation and/or supplied asset integration as requested.
- “Add CG to an existing patient” never creates or duplicates the patient. Confirm the patient bundle/index entry first.
- Full-nudity illustrations and NSFW CG are always supplied-asset imports for an already-existing patient. They are not part of new-patient data creation or required SFW generation.
- An omitted optional asset is not a failure and must not be generated or imported to make a checklist look complete. Conversely, an in-scope requested asset cannot be waived because it is optional in some other workflow.
- Preserve user-authored dialogue/plot text exactly unless the user explicitly authorizes edits. Do not fill narrative gaps to satisfy a schema; report a blocking conflict.
- Before editing, verify the repository root and inspect `git status`. Preserve unrelated user changes.
