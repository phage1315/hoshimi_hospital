# 手术系统 V2 五阶段实施计划

## 1. 目标与范围

手术系统 V2 将现有的四阶段线性术式扩展为更长、更有区别的手术流程，并让清醒患者在术中根据当前步骤、身体感受、麻醉方式和患者状态持续作出反应。

系统继续采用数据驱动的线性手术流程。第一轮不实现任意步骤跳转、技术数值模拟、并发症、支援值或随机失败。技术流程仍保持游戏化抽象，不制作现实医疗操作教学。

实施顺序固定为：

1. 患者互动引擎
2. 三台代表性术式垂直切片
3. 迁移和重写现有 25 种术式
4. 增加首批 6 种新术式
5. 人物专属互动与后续系统接口

## 2. 全局设计约束

### 2.1 手术中禁止存档

手术必须作为一次连续流程完成。进入实际手术以后，玩家不能手动保存，系统也不能自动保存。

建议以 `surgery_started` 为禁止存档的起点，以进入 `surgery_result` 或离开手术流程为终点：

```text
术前准备、团队选择、麻醉选择
  → 允许存档

确认开始手术并写入 surgery_started
  → 禁止手动存档
  → 禁止自动存档
  → 禁止覆盖已有存档

完成手术并进入 surgery_result
  → 恢复存档
```

UI 应在手术期间禁用“保存”按钮，并显示简短原因，例如“手术进行中，无法保存”。存档后端也必须独立拒绝请求，不能只依靠按钮状态。

载入存档只会回到开始手术以前的最后一次合法状态。现阶段没有需要迁移的玩家存档，因此 V2 可以直接改变阶段和事件结构，不保留旧手术事件回放兼容。

### 2.2 保持线性术式流程

V2 第一轮继续按照 `stages[]` 数组顺序推进：

```text
stages[0] → stages[1] → stages[2] → ... → completion
```

不增加任意 `next` 跳转或手术流程图。错误判断由团队成员纠正，玩家返回当前步骤重选。

### 2.3 数据职责分离

- `surgeries.json`：术式步骤、团队选择、互动主题和患者身体感受标签。
- `patient_interactions.json`：普通清醒患者互动及处理选项。
- `temporary_conditions.json`：恶心、昏沉等临时状态的触发、文本和处理方式。
- `data/patients/templates/preop.json`：术前准备、团队组成、麻醉、进入手术和手术完成的共用外层流程。
- `data/patients/<patient_id>/patient.json`：患者身份、性格、专属对白与专属 CG 覆盖。

术式文件不直接保存大批患者对白，共用 preop 模板也不承担可重复的术中患者互动节点。

### 2.4 确定性行为

第一轮不用随机数选择患者事件。匹配相同条件时，优先选择尚未在本台手术出现的第一条记录；全部使用过以后才从第一条重新循环。

临时状态使用确定性触发。这样便于测试、复现和调节内容密度。

## 3. 第一阶段：患者互动引擎

详细状态机、数据格式和三次可测试交付见 `docs/surgery_v2_phase1_deep_dive.md`。

### 3.1 目标

建立独立于 `preop` 节点的术中患者事件系统，使同一台手术可以多次出现不同互动，并支持患者状态、身体感受和临时状态。

### 3.2 Schema 工作

扩展 `surgery_flow_stage`：

- 扩大 `awake_interlude` 枚举：
  - `""`
  - `operative_contact`
  - `progress_check`
  - `strain_interaction`
  - `dignity_interaction`
  - `ongoing_interaction`
  - `closure_interaction`
- 增加必填 `patient_cues: string[]`。
- 第一版 cue：
  - `incision`
  - `pressure`
  - `traction`
  - `deep_manipulation`
  - `position_discomfort`
  - `exposure`
  - `fatigue`
  - `nausea`
  - `drowsiness`
  - `closure`

扩展 `surgery`：

- 增加必填 `procedure_group`。
- 第一版允许 `general_abdominal / female_pelvic / breast / urologic / thoracic / cardiac / vascular`。
- `procedure_group` 只描述术式类别，不承担患者身份或人物性格。

新增两个数组型数据集合，以适配当前 content loader：

```text
data/surgeries/patient_interactions.json
data/surgeries/temporary_conditions.json
```

普通互动至少包含：

```text
id
theme
states
cues
prompt
speaker
actions
procedure_groups
surgery_ids
once_per_surgery
```

互动 action 至少包含：

```text
id
label
response
response_speaker
delegate_role
minutes
effects
condition_effect
```

其中：

- `delegate_role` 只允许空值、`assistant_surgeon`、`circulating_nurse`。
- `effects` 只修改 `fear / pain / dignity / cooperation`。
- `condition_effect` 修改当前临时状态的严重度和剩余步骤。
- 第一轮临时状态仅支持 `nausea` 和 `drowsiness`。
- `procedure_groups`、`surgery_ids` 都为空时表示通用对白。
- 两者不能同时为非空；一条 variant 必须明确属于具体术式、术式类别或通用池中的一种。
- 具体术式优先于术式类别，术式类别优先于通用池；每层内部再按 state 和 cue 精确度匹配。

### 3.3 运行时工作

在 `preop_session.gd` 中把患者事件实现为 `surgery_flow` 内部子状态：

```text
手术步骤选择
  → 团队回应
  → 患者事件（若有）
  → 委托成员回应（若有）
  → 下一手术步骤
```

核心职责应拆分为独立函数：

- 计算当前 dominant patient state。
- 根据 surgery、procedure group、theme、state、cues 匹配普通互动。
- 创建和选择临时状态事件。
- 应用互动 action 的时间和四项状态效果。
- 应用临时状态效果。
- 在步骤结束时更新临时状态持续时间。
- 记录本台手术已使用的互动 ID。

事件顺序固定为：

```text
全麻检查
→ 更新此前已有的临时状态
→ 根据当前 stage cues 创建新临时状态
→ 选择最高严重度临时状态
→ 无临时状态时匹配普通互动
→ 每个 stage 最多出现一个患者事件
```

本阶段同时加入手术中的存档锁定。UI 与存档后端都必须执行该规则。

### 3.4 UI 工作

复用现有手术和患者互动界面，支持：

- 患者台词。
- 2–3 个处理选项。
- 当前 Fear、Pain、Dignity、Cooperation。
- 当前临时状态及严重度。
- 助手医生或巡回护士的委托回应。
- 返回手术步骤时清理患者事件 UI 状态。
- 手术中保存按钮的禁用状态和原因提示。

### 3.5 数据验证

验证器应检查：

- theme、state、cue、delegate role 合法。
- 互动 ID 全局唯一。
- 每个互动有 1–3 个 action。
- effects 不能修改技术数值。
- 临时状态 ID、severity 和 remaining steps 合法。
- 每种 theme 至少存在默认 fallback。
- 缺少精确组合时不会阻塞手术流程。

### 3.6 第一阶段验收

- 全麻路线不会生成或显示患者事件。
- 清醒路线可以在一台手术中连续触发多个不同事件。
- dominant state 按归一化严重度选择。
- 相同对白不会连续重复，且结果可复现。
- 相近患者指数在阑尾、子宫、乳房和心脏手术中能匹配到明显不同的内容。
- nausea 和 drowsiness 能创建、持续、处理和自然消失。
- 主刀、助手和巡回护士处理方式均能正确显示与结算。
- 每个步骤最多触发一个患者事件。
- 错误手术选择重试时不会重复结算患者事件。
- `surgery_started` 到 `surgery_result` 之间无法手动或自动保存。
- 数据验证和手术状态机测试通过。

## 4. 第二阶段：三台代表性术式垂直切片

### 4.1 目标

在批量重写内容以前，用三种不同规模和身体区域的术式验证节奏、互动密度和 UI。

### 4.2 代表术式

1. `surgery_appendix`：7 步，简单腹部手术。
2. `surgery_hysterectomy`：12 步，中型盆腔手术。
3. `surgery_open_whipple` 或 `surgery_cabg`：17–18 步，大型手术。

最终选择 Whipple 或 CABG 时，优先考虑现有病例、CG 和测试覆盖较完整的一项。

### 4.3 内容要求

- 新增阶段使用语义化 ID，不使用 `phase_01_stage` 一类编号占位符。
- `confirm` 只用于真正的阶段里程碑。
- 中大型手术包含多个 `decision`，不能只有一个正确判断点。
- 团队交流分散在手术前段、中段和关闭前。
- 患者互动密度符合手术长度，不在每个步骤都弹出。
- 乳房和盆腔类内容优先验证 dignity interaction。
- 腹部和长手术优先验证 traction、pressure、fatigue、nausea 和 drowsiness。

### 4.4 验收

- 简单手术不会显得被频繁互动打断。
- 中型手术能体现进度、疼痛和尊严变化。
- 大型手术能持续较长时间而不重复同一段患者对白。
- 全麻路线明显更快，以技术步骤和团队交流为主。
- 清醒路线的额外时间和状态变化能正确进入结果总结。
- UI 在 7、12、18 步规模下均保持清晰。

## 5. 第三阶段：迁移和重写现有 25 种术式

### 5.1 目标

把现有所有术式从统一四阶段扩展成具有各自节奏的 7–18 阶段流程。

扩展稿作为阶段范围和术式里程碑参考，不直接作为最终文本导入。

### 5.2 建议密度

| 手术规模 | 总步骤 | Decision | Flavor | 患者事件点 |
|---|---:|---:|---:|---:|
| 简单 | 7–8 | 1–2 | 1 | 2–3 |
| 中型 | 9–12 | 2–3 | 1–2 | 3–4 |
| 大型 | 13–16 | 3–4 | 2 | 4–6 |
| 极大型 | 17–20 | 4–5 | 2–3 | 5–7 |

这些数字是内容目标，必要时可按术式节奏调整，不应机械填满。

### 5.3 分批顺序

建议按内容类别迁移：

1. 常规腹部与疝修补。
2. 胃肠和结直肠。
3. 乳房、妇科与盆腔。
4. 泌尿与后腹膜。
5. 胸腔、食管、心脏和大血管。

每批完成后单独验证，避免一次修改全部 25 种后再集中排错。

### 5.4 验收

- 25 种术式全部通过 schema 和自定义验证。
- 每个术式的阶段 ID 在术式内部唯一且有明确语义。
- 不存在大批重复的“确认并继续 / 确认，可以继续”。
- 每个 decision 恰好有一个正确选项，错误选项有合理纠正。
- 每个术式的患者事件主题和 cue 与当前阶段相符。
- 各规模手术的长度和互动密度有明显区别。
- 所有现有病例、CG池和团队对白引用仍然有效。

## 6. 第四阶段：增加首批 6 种新术式

### 6.1 目标

在 V2 流程稳定后增加能带来新内容差异的术式，暂不一次加入全部候选。

### 6.2 首批建议

1. 开放式远端胰切除术。
2. 低位前切除术。
3. 开放式部分肾切除术。
4. 改良根治性乳房切除术。
5. 根治性子宫切除术或卵巢肿瘤减灭术。
6. 外科主动脉瓣置换术。

### 6.3 每种新术式的完整交付

- 术式定义和全部 stages。
- 病例模板、症状、检查和罕见变体。
- 通用手术进程 CG pool 映射。
- 所需术前准备分类。
- 手术时长和团队岗位。
- 患者互动主题与 cue。
- 至少一条能区别于已有术式的游戏判断。
- 验证器覆盖。

### 6.4 暂缓候选

Ross 手术、全盆腔脏器切除和多个相近瓣膜术式留到难度、解锁和专属病例系统成熟以后。

### 6.5 验收

- 每个新术式都有完整病例模板。
- 每个新术式恰好映射一个通用 progress CG pool。
- 新术式能进入术前准备、手术和结果流程。
- 新术式提供的玩法判断与已有术式有可辨认差异。

## 7. 第五阶段：人物专属互动与后续接口

### 7.1 目标

在通用互动池稳定后，让同一手术步骤因患者身份、性格、关系和医护担当患者而呈现不同内容。

### 7.2 内容层级

匹配优先级建议为：

```text
命名患者 + 特定术式/主题覆盖
→ 患者性格覆盖
→ 医护作为患者的职业覆盖
→ 通用 theme + state + cue
→ 通用 theme fallback
```

### 7.3 后续接口

本阶段可以加入或预留：

- Named Patient Dialogue Overrides。
- Patient Personality。
- 医护手术患者 play 的特殊对白。
- 关系等级和恋人关系对白。
- Fear Break。
- Dignity Break。
- Patient Experience Rating。
- Assistant Support。
- Circulating Nurse Patient Support。
- Scrub Nurse OR Support。
- Surgery Difficulty 和技术检定接口。

支援值、技术失败、出血、术野和并发症仍应分别设计，不能与患者互动系统隐式耦合。

### 7.4 验收

- 专属内容缺失时能安全回退到通用池。
- 同一患者在不同状态下仍能选择不同对白。
- 专属对白不会破坏临时状态事件。
- 医护担当患者时可以复用手术流程和患者事件引擎。
- 新增性格和人物不需要修改手术状态机。

## 8. 阶段依赖与完成顺序

```text
第一阶段：互动引擎
  ↓
第二阶段：三台垂直切片
  ↓
第三阶段：现有25术式
  ↓
第四阶段：首批6个新术式
  ↓
第五阶段：人物专属内容与后续接口
```

第一阶段决定数据契约和状态机；第二阶段决定内容节奏。只有这两阶段稳定以后，才适合批量制作其余术式和人物对白。

## 9. 当前明确不做

在第一至第三阶段内暂不实现：

- 任意步骤跳转。
- 分支手术流程图。
- 出血和术野模拟。
- 技术失败概率。
- 随机并发症。
- 助手或护士支援点消耗。
- 手术难度检定。
- 旧手术中存档兼容。
- 旧手术事件回放迁移。

这些内容只能在现有线性 V2 流程稳定后单独设计。
