# 通用特殊事件框架

特殊事件用于整日或连续多日的讲课、教学手术、医院祭、研修和重大病例。活动配置位于 `data/events/special_events/index.json`，每日脚本位于 `data/events/special_event_steps/index.json`。

活动配置负责：

- 解锁条件、硬性出场角色与前置事件
- 连续占用天数和每日脚本顺序
- 一次性／可重复规则
- 完成旗标和事件鉴赏解锁

每日脚本负责对白、人物差分、CG和选择分支。节点中的 `actor_id` 与 `outfit` 可按台词切换人物，因此同一活动可自然容纳多人互动。`@day_end` 会结束当天并自动进入下一日；最后一天结束后活动完成。

## 旁白边界

事件文本必须区分系统说明与角色表演。高级手术规则、术中状态、时间推进、场景转换和玩家无法从画面得知的客观结果，可以由旁白说明。角色的情绪、态度、关系和反应应优先交给台词、立绘、表情差分与简短可见动作。

角色节点只写镜头能够直接看见或听见的内容。例如可以写“她停了两秒，只点了一下头”，不要写“她很勉强地同意”；可以让角色改口、停顿或回避视线，不要由旁白解释她真正怎么想。删除“她显得……”“她意识到……”“所有人都明白……”“这说明……”等替观众下结论的句子。只有场景无法用现有立绘与台词表达，而且信息又确实影响理解时，才补最短的角色旁白。

同一节点原则上只表现一个说话者。多人连续对话或动作交接时，应在说话者切换处拆分节点，并为每个节点显示对应人物、服装与表情；旁白动作也可以配合动作执行者的立绘。只有刻意表现极快的齐声回应、通讯记录或系统汇总时，才把多名角色放在同一文本框中。

## 对话框容量与点击节奏

普通 VN 对话节点必须在默认 `1100 × 91` 文本区域内完整显示。编写时应把一次发言、一个可见动作或一个短旁白作为一个点击点；角色切换、旁白与发言切换、动作完成后进入下一句时，都应建立新的节点。不得依赖玩家拖动对话框滚动条来读完剧情。

运行时会把历史脚本中的显式换行和超长单行自动分页，选项只在最后一页出现。这是旧内容与不同语言字宽的安全网，不能代替新内容的分镜。新增或改写事件仍必须在数据里主动拆分节点，并为每个节点选择正确的说话人、立绘、服装与表情。

只有通讯记录、完整病历、制作人员名单或刻意设计为长文阅读的系统汇总，才可以设置 `allow_dialogue_scroll: true`。使用该例外时必须能说明为什么滚动本身属于演出的一部分；普通角色对白、动作旁白和教学说明均不属于例外。

## 原案保真与分镜

实现事件时应先把原案拆成分镜，再转换成运行节点。每个分镜明确当前说话者、可见动作、立绘或 CG、背景以及玩家输入；场景转换只补足必要的时间和地点信息。不得为了缩短脚本、突出教学系统或方便接入而自行合并、淡化、改写或删除原案中的角色桥段、关键台词、互动节奏与尺度意图。

如果某段内容的表现尺度、素材使用或实现边界存在疑问，应在修改前向用户指出具体段落和疑问，等待用户决定。不得以潜在尺度问题为由自主审查、静默删减、改成含蓄版本或用系统说明替代角色内容。

事件可在活动配置中设置 `cg_dialogue_delay_seconds`。新 CG 首次出现时，系统先完整显示画面，经过指定秒数后再显示对话框与按钮；连续节点沿用同一张 CG 时不重复等待。千束高级转诊事件统一使用两秒，以免对白框立刻遮住新画面。

单日活动也可以在多个地点之间推进。节点可用 `background_id` 覆盖每日脚本的默认背景；下一节点没有覆盖时重新使用脚本默认背景。非 staff 的来访者和患者可以通过 `speaker_label` 配合 `portrait_path` 显示姓名与事件专用透明立绘，无需伪装成医院职员。

活动可以使用 `relationship_rewards` 在完成时推进人物等级。通常只允许从当前等级升一级；`allow_level_skip` 仅供尚未完成前置关系事件时的内容测试，正式发布前必须移除。

## 支持的条件

- `staff_unlocked`
- `relationship_level`
- `flag`
- `character_event_completed`
- `special_event_completed`
- `completed_surgeries`
- `completed_surgeries_in_group`
- `player_attribute`
- `day_number`
- `month_number`（真实公历月份，4–12 月后进入次年 1–3 月）
- `calendar_date`
- `calendar_range`
- `weekday`
- `day_type`

条件对象既可写在活动的 `unlock_requirements`，也可写在节点选择的 `requirements`。`required_characters` 是必须已认识的成员；`PLAYER` 永远视为已解锁。`prerequisite_events` 可以引用人物事件或其他特殊事件。

## 日程、优先级与年度边界

可选的 `timing` 对象包含：

- `trigger_day`：计划首次触发的游戏日
- `trigger_date`：固定公历日期，与 `trigger_day` 二选一，例如 `2025-12-24`
- `priority`：日程优先级，数字越大越优先
- `final_week_allowed`：是否属于可以占用最终周的特殊剧情
- `sunday_start_allowed`：是否明确允许在星期日开场；省略时为 `false`

系统在活动开始前检查整个占用区间。如果低优先级活动会与尚未完成、且已经满足基础条件的高优先级活动相撞，低优先级活动不会丢失，而是在高优先级活动结束后的可用日重新参与排期。

游戏年度为 365 天。第 359–365 天默认保留给结局和指定剧情；普通活动不能在这一周开始，也不能从前一周跨入。只有 `final_week_allowed: true` 的事件可以占用最终周，并且其最后一个活动日仍不得晚于第 365 天。

普通通用活动不会在星期日新开场；到期日落在星期日时保留为待触发，并在星期一重新参与排期。固定节庆、重大病例或强制剧情确实需要占用星期日时，必须写 `sunday_start_allowed: true`。这个限制只检查活动的开场日：周六已经开始的连续多日活动可以自然经过星期日，进行中的活动锁也始终优先于星期日自由菜单。

## 运行与回放

活动开始前统一显示占用天数确认。开始后 `active_mode` 锁定为 `special_event`，地图、闲谈、人物事件和其他耗时行动不会介入。存档保存当前活动、天数、节点与选择历史，读档后继续原阶段。

事件鉴赏使用独立的 `SpecialEventSession`。回放只重放脚本，不调用 `GameState.choose_special_event()`，因此不会推进日期、重复设置旗标或修改世界状态。

两个 `developer_only` 示例覆盖单日与三日流程，不会出现在正式活动列表或鉴赏列表中；自动测试会直接使用它们验证框架。
