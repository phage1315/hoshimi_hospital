# 深山 Lv1《叮。》触诊占位的具体含义

## 事件内实际发生什么

事件 miyama_01_safety_pin，步骤 miyama_01_safety_pin_main 的顺序为：

recheck（坂口让团队暂停重查）→ palpation_placeholder → decision → merge → continue_op。

palpation_placeholder 的正文明确写“完整触诊玩法将在后续制作；本次按固定剧情结果继续”。它只有一个按钮“一键跳过触诊”，直接进入 decision。没有创建公共 PreopSession 触诊会话，也没有工具、部位、力度选择或触诊结果回传。

结果已由原文固定：患者恐惧、紧绷，疼痛定位和腹壁反应无法可靠解释。随后可以选择先取消重评或认为风险尚存；两者汇合至深山仍不能排除问题并继续准备的剧情。不是玩家做一次真实触诊后计算出的结果。

## 公共触诊与麻醉测试已经实现

公共诊疗使用 godot/systems/preop_session.gd 的 or_table_palpation 与 anesthesia_sensory_test 阶段，godot/ui/preop_view.gd 的 render_or_table_palpation 共用界面，区分麻醉前触诊和麻醉后的感觉确认。

公共界面能接收工具/部位等输入，并维护当次患者反应。这套功能存在，不会自动让《叮。》的特殊事件节点变成可操作界面；两者是不同的会话和推进路径。

## 解锁 flag 目前做什么

事件 completion_flags 包含 or_table_palpation_unlocked，结束时与其他稳定结果一起写入。当前 godot 生产逻辑没有读取这个 flag 作为触诊或麻醉测试的入口条件。因此它现在记录一个完成事实，并没有真正控制这两项功能是否开放。

该事件的 rank 提示还写“解锁接口：手术台术前触诊（占位）”。这与当前公共功能已存在的情况产生了时间上的落差，但不能未经授权删改用户文本。

## 若后续接通，需要明确的两件事

1. 剧情内互动：是否实际调用公共界面，以及触诊结果是否仍固定汇入原稿。涉及剧情控制、患者状态、耗时和退出返回，不能仅替换一个按钮。
2. 全局解锁：是否让 or_table_palpation_unlocked 同时控制公共触诊与麻醉感觉测试。只有将它接入真实入口判断，才构成同步解锁；当前没有该绑定。
