# 星见医院：普通闲谈补写交接稿

日期：2026-10-13  
用途：交给写作 GPT，补齐当前“角色会在休息室／天台出现，却没有闲谈入口”的内容缺口。  
状态：需求与参考材料；本文件不包含新写的正式台词，也不表示新增闲谈已实装。

## 1. 本批写什么

- 共 **10名角色、17组“角色×地点”、51段中文闲谈**。
- **休息室：10人，每人3段，共30段。**
- **天台：7人，每人3段，共21段。**
- 每段为独立随机备选，不能拆成连续播放的上、中、下三段。
- 不覆盖、不改写已有79段闲谈；不编写带选项的微事件、关系事件、约会或下班同行。
- 本批先交中文，定稿后由实装方同步英文、注册数据并验证；技术ID与地点ID不可翻译。

## 2. 展示方式与写作约束

当前普通闲谈读取角色的 `time_events.json`，每次从该地点的 `responses` 随机选一段，可能连续抽到同一段。界面显示该角色的名字与立绘，正文是一段完整文本；不会按台词自动切换说话人。

- 推荐“简短动作／情境 + 角色直接对白”，也可用简洁叙述式。可含坂口的回应，但须在正文中明确是谁说话，不写成需要独立说话人节点的剧本。
- 每段建议约40–120个汉字、1–3句，只是篇幅建议，不是强制技术上限。避免为凑字数添加无关旁白。
- 休息室侧重短暂休息、同事相处与生活侧面；天台侧重透气、观察与更安静的交流。不要求每段都谈工作，也不要求天台每段都谈沉重心事。
- 每组3段尽量话题、开场动作和收尾各异；不要只是换形容词。不同场合也不要复制同一句改地点。
- 当前入口只有相识／在场等条件，不按关系等级为不同段落分层；正文须适用于已认识但未恋爱的同事。不要预设已约会、已表白、私人秘密已公开或关系剧情已完成。
- 地点可以在不同日期、时段遇见；不要无条件写死“刚做完手术”“熬了一整夜”“今天是周日”“刚吃过午饭”等前情。若创意必须依赖这些条件，单列为以后需条件支持的提案，不混入本批51段。
- 不包含选项、分支、触发字段、新增记忆旗标、关系升阶或奖励设计；当前30分钟耗时与可重复规则由代码保留，不由文案改动。
- 使用下文确认过的本项目设定。缺少背景、爱好、家庭经历等依据时不要自行补成事实；可向用户询问或标注待确认。
- 人物特色来自注意的细节、判断方式和回应，不把每人压缩成一种口癖。幽默不能以破坏专业可靠性或患者安全为代价。
- 下文“写作方向”为本次建议，不是新增人物正史，也不是必须写出的剧情。

## 6. 当前数据结构示例

下面是现有小夜香休息室入口的完整对象。角色文件整体是一个JSON数组，可包含多个地点对象。

```json
{
  "id": "lounge_chat_doc_sayaka",
  "location_id": "lounge",
  "label": "和南条小夜香闲聊",
  "actor_id": "doc_sayaka",
  "responses": [
    "南条端着咖啡坐到对面：“你可以把这理解成休息，也可以理解成我主动制造一次偶遇。”",
    "她聊起以前在学校保健室工作的两年，说自己在那里学会了同一句“肚子痛”可能藏着十种完全不同的问题。",
    "坂口问她为什么总能在不同科室出现。南条笑道：“因为我没有最强的地方。换个说法，就是大多数地方都能帮一点。”"
  ],
  "minutes": 30,
  "repeatable": true
}
```

- `actor_id`：固定角色技术ID。
- `location_id`：场合，本批仅 `lounge`／`rooftop`。
- `responses`：独立备选正文；数组每项是一段，而不是一句连续台词。
- `id`：入口技术ID，沿用 `lounge_chat_<actor_id>`／`rooftop_chat_<actor_id>` 命名，由实装方核对唯一性。
- `label`：入口描述；实际地点界面通常显示“闲谈 · 30分钟”。
